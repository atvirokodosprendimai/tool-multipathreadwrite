# Native performance baseline — pre-registration (DRAFT, not yet agreed)

**Status:** draft for Zy, 2026-10-28. Nothing below has been run. Once agreed, this file is merged BEFORE the
first measurement, and no workload, metric, threshold or budget changes after the first number is seen; a
change after that is a new pre-registration with its own date, and the earlier one is reported beside it.

**Why.** Robustness plan item 3 (memoryd tool-multipathreadwrite/644d167a): a current-release baseline before
any optimisation, so an optimisation is chosen from a reproduced bottleneck, not a guess. This is a native
benchmark of the binary. It says nothing about agent task cost, tokens or accuracy (that is item 4, `docs/bench/`).

## What is measured

The released binary **v1.77.1 (926aaba)**, downloaded from the GitHub release (`mrw-darwin-arm64`, checked against the release's `SHA256SUMS.txt`), its sha256
recorded, beside a source build of the head under test with the release flags (`CGO_ENABLED=0 go build -trimpath -ldflags "-s -w -X main.version=…"`, as `.github/workflows/ci.yml:297` builds the release).
Every number names which binary it came from.

| Id | Workload | Sizes |
|----|----------|-------|
| R1 | `mrw read F:A-B`, one range | F of 100 / 10,000 / 1,000,000 lines; the range 40 lines at the middle |
| R2 | `mrw read` with W specs across W files | W = 1, 10, 100; files of 1,000 lines |
| R3 | `mrw read --grep P .` over a tree | this repository at the tagged tree; a synthetic 3,000-file tree (BenchmarkWalkDeep131's shape) |
| W1 | `mrw write --no-check` of a plan, H hunks over F files | (H, F) = (1, 1), (50, 10), (500, 50) |
| W2 | `mrw write --grep --sub --no-check` | the same edit at 10 / 1,000 sites |
| L1 | R1 at 10,000 lines with a ledger of E entries | E = 0, 1,000, 10,000 |
| C1 | first use (no state directory) vs warm (state directory and ledger exist) | R1 at 10,000 lines |

Fixtures are generated by a committed script from a fixed seed; the script and its sha256 are named in the result.

## How

- **Machine:** this Mac (Apple M5, 10 cores, 32 GB), on AC power, recorded with `sw_vers`, `go version`
  (go1.27.3 for the source build), and `sysctl -n vm.loadavg` before and after every workload.
- **Load gate:** a workload starts only when the 1-minute load average is below 2.0; above it, the run waits
  (bounded, 10 minutes) and then stops with `load` recorded, never measuring under contention.
- **Repetitions:** 5 warm-up runs discarded, then 30 timed runs per workload and size, interleaved between the
  two binaries (A, B, A, B …) so drift falls on both.
- **Metrics:** wall time p50, p90 and max (per-process, `time.Now` around `exec` in a small Go driver, or
  `hyperfine` if installed — the tool is named); user+sys CPU from `ProcessState`; peak RSS (`/usr/bin/time -l`);
  stdout bytes; for the in-process paths, `go test -bench` allocations (`-benchmem`) on the existing
  `BenchmarkWalkDeep131` and `BenchmarkResolveADeepFile` plus R1/W1 benchmarks added for this.
- **Raw data:** every timing kept, in `docs/bench/native-baseline/raw/`, failures included; a run that exits
  non-zero is recorded and counted, not dropped.

## Budget

At most **15 minutes of wall time** in total for the whole baseline, measured, and at most two sessions; it
runs alone (no other build or suite of this session at the same time). If a pass would exceed it, the largest
sizes (1,000,000 lines, 500 hunks) are dropped first and that is recorded.

## What counts as a bottleneck, and what an optimisation must show

- A **candidate bottleneck** is a workload whose p50 exceeds 100 ms, or whose time or allocations grow faster
  than linearly in its size between two adjacent sizes (ratio of time over ratio of size above 1.5).
- A candidate is **profiled** (`-cpuprofile`, `-memprofile`) before any code is changed; the profile, not the
  timing, names the function.
- An optimisation is **kept** only when, on the same workloads, machine and load gate, its p50 improves by at
  least 20% with the two 30-run intervals (p25–p75) not overlapping; every gate in AGENTS.md passes; no guard,
  licence or bound changes (robustness rules, memoryd 36c1d382, rule 4). Otherwise it is reverted and the result
  reported as no gain.
- **No candidate is a result too.** "Nothing over 100 ms and nothing super-linear" ends item 3 with no code change.

## What this will not claim

- Nothing about agent task time, tokens or cost: fewer calls or bytes are not those (item 4).
- Nothing about Windows or Linux: macOS arm64 only; a Windows baseline is a separate registration.
- No comparison with another tool.
